# ADR-001: Message Codec Design
**Version:** 1.0    
**Status:** Accepted    
**Date:** 2026-11-03    
**Target:** C++20 to demonstrate proficiency; C++23 migration planned

## Context
A Codec to encode and decode the bit-packed messages defined in the specs is required.
See [Pitch Tracker Specification](../Specs/Pitch-Tracker.md).

## Decision
- Bit order: MSB-first within each byte
- Field widths: 1-64 bits, uint64_t
- Errors: functions return `cf::Result<T>`, holding either a value or a
  `cf::DecodeError` code, modeled on `std::expected` so it can be replaced
  when the project moves to C++23.
- Padding: encoder writes zeros; decoder ignores padding bits so they can be used for future fields without breaking existing messages.
- Year: uses 12 bits to allow for a raw year to be readable in hex dumps.

## Consequences
- Positive:
  - Errors are part of each function's signature, so callers must handle them
    (`[[nodiscard]]` makes ignoring a result a compiler warning).
  - No exceptions, consistent with the Google C++ Style Guide.
  - MSB-first matches the specs' byte layout, so hex dumps read left to right
    in field order.
  - `cf::Result<T>` mirrors `std::expected`, keeping the C++23 migration small.
- Negative / Tradeoffs:
  - `cf::Result<T>` is a custom type to write, test, and maintain until C++23.
  - Every call site must check the result, which is more verbose than exceptions.
  - Fields are limited to 64 bits by the `uint64_t` container.

## Alternatives Considered
- LSB-first: rejected because the specs define fields MSB-first and big-endian;
  LSB-first would make encoded bytes harder to read against the spec tables.
- `std::expected`: rejected because it requires C++23.
- Exceptions: rejected because the Google C++ Style Guide disallows them.
