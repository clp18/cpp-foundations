# ADR-001: Message Codec Design
**Version:** 1.1    
**Status:** Accepted    
**Date:** 2026-11-08    
**Target:** C++20 to demonstrate proficiency; C++23 migration planned

## Context
A Codec to encode and decode the bit-packed messages defined in the specs is required.
See [Pitch Tracker Specification](../Specs/Pitch-Tracker.md).

## Decision
- Bit order: MSB-first within each byte
- Field widths: 1-64 bits, uint64_t
- Errors: functions return `cf::Result<T, E>`, holding either a value of type `T` or an error of type `E`. Errors are created with `cf::Unexpected(e)`. Both are modeled on `std::expected` / `std::unexpected` so they can be replaced when the project moves to C++23.
- Error types are layered: `cf::CodecError` covers bit-level failures (buffer too short, invalid width). Each message defines its own enum for validation failures. Decoders convert codec errors into their message's errors, so caller handles one enum per message.
- Calling `value()` on an error, or `error()` on a value, calls `std::abort`.  This misuse is a programmer bug, not a run time failure, and exceptions are not allowed by the Google coding standards.
- Operations with no result value return `cf::Result<void, E>`, a specialization matching `std::expected<void, E>`. Success is `return {};`.
- Padding: encoder writes zeros; decoder ignores padding bits so they can be used for future fields without breaking existing messages.
- Year: uses 12 bits to allow for a raw year to be readable in hex dumps.

## Consequences
- Positive:
  - Errors are part of each function's signature, so callers must handle them. `[[nodiscard]]` makes ignoring a result a compiler warning, which this project's `-Werror` build turns into an error.
  - No exceptions, consistent with the Google C++ Style Guide.
  - MSB-first matches the specs' byte layout, so hex dumps read left to right
    in field order.
  - `cf::Result<T, E>` mirrors `std::expected`, keeping the C++23 migration small.
- Negative / Tradeoffs:
  - `cf::Result<T, E>` and `cf::Unexpected<E>` are custom types to write, test, and maintain until C++23. 
  - `cf::Result<T, E>` is designed to allow for easy migration to `std::expected`. 
    As a result NOLINT comments will be used to keep the `std::expected` member names (`has_value`, `value`, `error`), which the naming rules would otherwise flag.
    allow same naming structure of functions without coding standard violations.
  - Every call site must check the result, which is more verbose than exceptions.
  - Fields are limited to 64 bits by the `uint64_t` container.

## Alternatives Considered
- LSB-first: rejected because the specs define fields MSB-first and big-endian;
  LSB-first would make encoded bytes harder to read against the spec tables.
- `std::expected`: rejected because it requires C++23.
- Exceptions: rejected because the Google C++ Style Guide disallows them.
